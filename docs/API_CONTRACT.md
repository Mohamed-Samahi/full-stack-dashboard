# Full-Stack Dashboard — API Contract

> **Status:** Implemented API  
> **Repository:** [Mohamed-Samahi/full-stack-dashboard](https://github.com/Mohamed-Samahi/full-stack-dashboard)  
> **Backend
> directory:** `/backend`  
> **API version:** v1  
> **Last reviewed:** November 2, 2026  
> **Total endpoints:** 17

This document defines the backend API contract for frontend development. It
covers authentication, authorization, request validation, response structures,
errors, and integration requirements.

All documented endpoints have been verified against the backend source code
rather than inferred from planned features.

---

## 1. API Overview

### Base URL

Development server:

```text
http://localhost:5000
```

API prefix:

```text
/api/v1
```

Endpoint groups:

| Module                    | Base Path      | Endpoints |
| ------------------------- | -------------- | --------- |
| Authentication            | `/api/v1/auth` | 10        |
| Role-Based Access Control | `/api/v1/rbac` | 7         |
| **Total**                 |                | **17**    |

The development port defaults to `5000` but can be overridden using the `PORT`
environment variable.

No production API hostname is defined in the reviewed backend source.

### Request Content Type

For endpoints accepting JSON:

```http
Content-Type: application/json
```

Authenticated requests additionally require:

```http
Authorization: Bearer <accessToken>
```

### Standard Response Conventions

Successful responses use one of these patterns:

```json
{
  "data": {}
}
```

```json
{
  "message": "Operation completed successfully",
  "data": {}
}
```

Some endpoints return only `message`. Successful `204 No Content` responses have
no body.

**Important:** The backend does not use a universal success envelope containing
fields such as `success`, `status`, or `code`.

### Common Error Responses

Application errors:

```json
{
  "status": "error",
  "message": "Error description"
}
```

Validation errors:

```json
{
  "status": "error",
  "message": "Validation failed",
  "errors": [
    {
      "code": "invalid_type",
      "path": ["email"],
      "message": "Invalid input: expected string, received undefined"
    }
  ]
}
```

Validation issues are generated by Zod. Their exact `code`, `path`, and
`message` depend on the invalid input.

Unexpected server errors:

```json
{
  "status": "error",
  "message": "Internal server error"
}
```

### HTTP Status Codes

| Code  | Meaning                                                               |
| ----- | --------------------------------------------------------------------- |
| `200` | Request completed successfully                                        |
| `201` | Resource successfully created                                         |
| `204` | Operation succeeded without a response body                           |
| `302` | HTTP redirect during Google OAuth initialization                      |
| `400` | Invalid payload, OAuth state, reset token, or business-rule violation |
| `401` | Missing, invalid, expired, or revoked authentication                  |
| `403` | Authenticated user lacks the required permission                      |
| `404` | Requested user or role not found                                      |
| `409` | Conflict, duplicate resource, or prohibited state change              |
| `429` | Password-recovery rate limit exceeded                                 |
| `500` | Unexpected server error or configuration failure                      |

No global API 404 JSON handler is explicitly registered in the reviewed
application. Unmatched routes may therefore return Express's default 404
response instead of the application's JSON error format.

## 2. Authentication Architecture

The application uses JWT-based authentication with refresh-token rotation.

### Access Token

- Returned in the JSON response after successful login, Google OAuth callback,
  or token refresh.
- Must be included in the `Authorization` header for protected endpoints.
- Contains the user's current role and permissions.
- Has an expiration configured by `JWT_ACCESS_EXPIRES_IN`.
- Is invalidated when the associated user or role authorization version changes.

Access JWT payload:

```ts
interface AccessTokenPayload {
  userId: string
  roleId: string
  role: string
  permissions: string[]
  roleVersion: number
  userVersion: number
  iat: number
  exp: number
}
```

JWT standard claims `iat` and `exp` are generated by the JWT library.

The frontend must treat the JWT as an opaque authentication credential. It
should use `/auth/me` to retrieve the authoritative user profile and effective
permissions.

### Refresh Token

The refresh token is an HTTP-only cookie set by the backend.

| Property    | Value                                   |
| ----------- | --------------------------------------- |
| Cookie name | `refreshToken`                          |
| HttpOnly    | `true`                                  |
| Secure      | `true` in production, `false` otherwise |
| SameSite    | `Strict`                                |
| Max-Age     | `JWT_REFRESH_EXPIRES_IN_SECONDS * 1000` |
| Path        | `/` (default cookie path)               |

The refresh token:

- Is not returned in JSON.
- Is stored as a SHA-256 hash in Redis.
- Is consumed atomically during refresh.
- Is replaced with a new refresh token after a successful refresh.
- Is invalidated when the user's authorization version changes.
- Is deleted from Redis during logout when supplied.

**Frontend requirement:** Never attempt to read `refreshToken` using
`document.cookie` or browser JavaScript. The cookie is HTTP-only.

Browser requests requiring the refresh cookie should use:

```ts
credentials: 'include'
```

For Axios:

```ts
withCredentials: true
```

**Cross-origin limitation:** The reviewed Express application does not configure
CORS middleware. A frontend running on a different origin from the backend
cannot assume that browser credentialed requests will work until CORS or a
same-origin proxy is configured.

The `SameSite=Strict` refresh cookie also requires a compatible site-level
deployment setup.

### 3.1 Register User

`POST /api/v1/auth/register`

**Purpose:** Create a new user account with the configured default role.

**Authentication:** Not required.

#### Request Body

```json
{
  "name": "John Doe",
  "email": "john@example.com",
  "password": "Password123!"
}
```

#### Validation

| Field      | Type   | Required | Rules                |
| ---------- | ------ | -------- | -------------------- |
| `name`     | string | No       | Minimum 2 characters |
| `email`    | string | Yes      | Valid email address  |
| `password` | string | Yes      | Minimum 8 characters |

The backend Zod schema does not explicitly trim or lowercase the registration
email.

Unknown JSON object keys are stripped by Zod's default object behavior.

#### Success — `201 Created`

```json
{
  "message": "User registered successfully",
  "data": {
    "id": "user-uuid",
    "name": "John Doe",
    "email": "john@example.com",
    "role": {
      "id": "role-uuid",
      "name": "USER"
    },
    "createdAt": "2026-11-02T10:00:00.000Z",
    "updatedAt": "2026-11-02T10:00:00.000Z"
  }
}
```

The actual role name is determined by `DEFAULT_USER_ROLE`. `USER` is the
expected seeded default.

`name` may be `null` if omitted.

#### Errors

| Status | Message / Reason                                        |
| ------ | ------------------------------------------------------- |
| `400`  | Validation failed                                       |
| `409`  | `User already exists`                                   |
| `500`  | `Default USER role is not configured`                   |
| `500`  | Missing environment configuration or unexpected failure |

#### Frontend Notes

- Registration does **not** automatically authenticate the user.
- No access token or refresh cookie is issued.
- After registration, redirect the user to the login page.
- Display duplicate-email errors using the returned `message`.

### 3.2 Login

`POST /api/v1/auth/login`

**Purpose:** Authenticate an existing password-based account.

**Authentication:** Not required.

#### Request Body

```json
{
  "email": "john@example.com",
  "password": "Password123!"
}
```

#### Validation

| Field      | Type   | Required | Rules       |
| ---------- | ------ | -------- | ----------- |
| `email`    | string | Yes      | Valid email |
| `password` | string | Yes      | Non-empty   |

#### Success — `200 OK`

```json
{
  "message": "User logged in successfully",
  "data": {
    "accessToken": "<jwt-access-token>"
  }
}
```

Additionally, the server sets:

```http
Set-Cookie: refreshToken=<token>; HttpOnly; SameSite=Strict; Path=/
```

The cookie will also have an expiration and production-dependent `Secure`
attribute.

#### Errors

| Status | Message / Reason      |
| ------ | --------------------- |
| `400`  | Validation failed     |
| `401`  | `Invalid credentials` |
| `500`  | Unexpected failure    |

Invalid email, incorrect password, and accounts without a local password use the
same `401 Invalid credentials` response.

#### Frontend Notes

After successful login:

1. Save the access token in application auth state.
2. Call `GET /auth/me`.
3. Populate the current user's profile, role, and permissions.
4. Redirect to the appropriate authenticated page.

**Recommended:** Keep the access token in memory rather than persistent browser
storage when the application's session architecture supports this.

### 3.3 Start Google OAuth

`GET /api/v1/auth/google`

**Purpose:** Start the Google authentication flow.

**Authentication:** Not required.

#### Request

No request body or required query parameters.

#### Success — HTTP Redirect

The backend:

1. Generates a random OAuth `state`.
2. Stores its SHA-256 hash in Redis for 5 minutes.
3. Sets an HTTP-only `google_oauth_state` cookie.
4. Redirects the browser to Google's authorization endpoint.

The OAuth state cookie uses:

| Property | Value                          |
| -------- | ------------------------------ |
| Name     | `google_oauth_state`           |
| HttpOnly | `true`                         |
| SameSite | `Lax`                          |
| Secure   | Production only                |
| Max-Age  | 5 minutes                      |
| Path     | `/api/v1/auth/google/callback` |

#### Frontend Integration

Start Google authentication using browser navigation:

```ts
window.location.href = `${API_BASE_URL}/auth/google`
```

Do not expect this endpoint to return JSON.

#### Errors

Unexpected server or Redis errors return `500`.

### 3.4 Google OAuth Callback

`GET /api/v1/auth/google/callback`

**Purpose:** Complete the Google OAuth authorization flow.

**Authentication:** OAuth authorization code and state.

This is a backend callback endpoint intended to be called by Google's redirect,
not directly by the frontend.

#### Query Parameters

| Parameter | Type   | Required                     | Description                                      |
| --------- | ------ | ---------------------------- | ------------------------------------------------ |
| `code`    | string | For successful authorization | Google's authorization code                      |
| `state`   | string | Yes                          | OAuth state matching the cookie and Redis record |
| `error`   | string | No                           | OAuth error returned by Google                   |

#### Success — `200 OK`

```json
{
  "message": "Google authentication successful",
  "data": {
    "accessToken": "<jwt-access-token>"
  }
}
```

The backend also sets the normal `refreshToken` HTTP-only cookie.

#### Processing

- Validates the OAuth state against the cookie and Redis.
- Exchanges the authorization code for Google tokens.
- Verifies the Google ID token.
- Requires a valid, verified Google email.
- Finds an existing linked OAuth account or creates a new user.
- Assigns the configured default role to newly created users.
- Issues an access token and refresh cookie.

#### Errors

| Status | Message                                                       |
| ------ | ------------------------------------------------------------- |
| `400`  | `Invalid Google OAuth state`                                  |
| `400`  | `Invalid OAuth state`                                         |
| `400`  | `OAuth state expired or already used`                         |
| `400`  | `Google authentication cancelled`                             |
| `400`  | `Google authentication failed`                                |
| `400`  | `Google authorization code is missing`                        |
| `400`  | `Google authorization code is invalid or expired`             |
| `401`  | `Google ID token is missing`                                  |
| `401`  | `Invalid Google ID token`                                     |
| `401`  | `Google account identity is invalid or email is not verified` |
| `409`  | `Account already exists. Account linking is required.`        |
| `500`  | Unexpected failure                                            |

#### Critical Frontend Notes

**The callback currently returns JSON directly instead of redirecting to a
frontend callback page.**

Consequently, standard browser navigation to `/auth/google` ends at a backend
JSON response after successful authentication.

A complete SPA integration would require an additional backend-to-frontend
handoff mechanism.

This is an implementation gap, not an undocumented frontend endpoint.

**Account linking is not implemented.** If a user already exists with the same
email but does not have a linked Google identity, the backend returns `409`
instead of automatically linking the accounts.

### 3.5 Refresh Access Token

`POST /api/v1/auth/refresh`

**Purpose:** Rotate the refresh token and obtain a new access token.

**Authentication:** Valid refresh-token cookie.

#### Request

No JSON body required.

Required cookie:

```http
Cookie: refreshToken=<refresh-token>
```

#### Success — `200 OK`

```json
{
  "data": {
    "accessToken": "<new-jwt-access-token>"
  }
}
```

The backend replaces the existing refresh cookie with a new one.

#### Errors

| Status | Message                            |
| ------ | ---------------------------------- |
| `401`  | `Refresh token is required`        |
| `401`  | `Invalid or expired refresh token` |
| `401`  | `Invalid or revoked refresh token` |
| `401`  | `User not found`                   |
| `500`  | Unexpected failure                 |

#### Refresh Token Rotation

Each refresh token is single-use.

On successful refresh:

1. The previous refresh token is atomically removed from Redis.
2. The current user and role permissions are loaded.
3. A new refresh token is generated and stored.
4. A new access JWT is generated.
5. The response sets the new refresh cookie.

Concurrent refresh attempts using the same cookie can cause all but one attempt
to fail with `401`.

#### Frontend Notes

- Use a single-flight refresh mechanism to prevent simultaneous refresh
  requests.
- Retry failed protected requests only after a successful refresh.
- If refresh returns `401`, clear authenticated frontend state and redirect to
  login.
- Do not retry the refresh endpoint recursively.
- A successful refresh can update role and permission claims.

```json
    "updatedAt": "2026-11-02T10:00:00.000Z"
  }

```

The permission list depends on the current database role assignments.

#### Errors

| Status | Message                    |
| ------ | -------------------------- |
| `401`  | `Authentication required`  |
| `401`  | `Invalid or expired token` |
| `401`  | `Invalid or revoked token` |
| `404`  | `User not found`           |
| `500`  | Unexpected failure         |

#### Frontend Notes

This endpoint is the primary source for:

- Current user information.
- Navigation visibility.
- Role and permission-aware UI.
- Protected frontend routes.

independently.

### 3.7 Logout

`POST /api/v1/auth/logout`

**Purpose:** Terminate the current refresh session.

**Authentication:** No Bearer token required; refresh cookie optional.

#### Request

No JSON body required.

When supplied, the `refreshToken` cookie is used to delete the corresponding
Redis session.

#### Success — `204 No Content`

No JSON response body.

The backend clears the `refreshToken` cookie.

#### Frontend Notes

- Logout is idempotent from the frontend perspective.
- Clear the in-memory access token and user state after a successful response.
- Redirect the user to the login page.
- Do not call `response.json()` for a `204` response.
- Cookie deletion should be performed using `credentials: "include"` for
  supported browser deployments.

The backend does not maintain an access-token blacklist for logout. An
already-issued access token may remain valid until expiration or another
revocation event.

### 3.8 Forgot Password

`POST /api/v1/auth/forgot-password`

**Purpose:** Request a password-reset email.

**Authentication:** Not required.

#### Request Body

```json
{
  "email": "john@example.com"
}
```

#### Validation

| Field   | Type   | Required | Rules                            |
| ------- | ------ | -------- | -------------------------------- |
| `email` | string | Yes      | Valid email, trimmed, lowercased |

The schema is strict: unknown fields are rejected.

#### Success — `200 OK`

```json
{
  "message": "If an eligible account exists, a password reset email will be sent."
}
```

#### Behavior

- Checks the source IP rate limit.
- Applies an email-specific cooldown.
- Looks up the user.
- Generates a cryptographically random reset token for eligible password-based
  accounts.
- Stores the hashed token in PostgreSQL.
- Sends an email using Resend.
- Does not reveal whether an account exists.

Google-only accounts do not receive a reset email.

#### Rate Limits

| Rule          | Limit                            |
| ------------- | -------------------------------- |
| Per source IP | 10 requests per 60-second window |
| Per email     | 1 reset request per 60 seconds   |

#### Errors

| Status | Message                                      |
| ------ | -------------------------------------------- |
| `400`  | Validation failed                            |
| `429`  | `Too many requests. Please try again later.` |
| `500`  | Unexpected failure                           |

Email delivery errors are logged internally and do not change the generic
success response.

#### Frontend Notes

Always display the generic confirmation message. Do not tell users whether the
email exists in the system.

The generated reset email points to:

```text
{FRONTEND_URL}/reset-password?token=<reset-token>
```

The frontend must implement a corresponding `/reset-password` route.

### 3.9 Reset Password

`POST /api/v1/auth/reset-password`

**Purpose:** Set a new password using a valid reset token.

**Authentication:** Reset token supplied in request body.

#### Request Body

```json
{
  "token": "64-character-hexadecimal-reset-token",
  "newPassword": "NewPassword123!"
}
```

#### Validation

| Field         | Type   | Required | Rules                             |
| ------------- | ------ | -------- | --------------------------------- |
| `token`       | string | Yes      | Exactly 64 hexadecimal characters |
| `newPassword` | string | Yes      | 8–72 characters                   |

The schema is strict: unknown fields are rejected.

The token supports uppercase or lowercase hexadecimal characters.

#### Success — `200 OK`

```json
{
  "message": "Password reset successfully. Please log in again."
}
```

#### Behavior

- Validates the reset token.
- Enforces single-use token consumption.
- Verifies the 15-minute expiration.
- Updates the user's password.
- Increments `user.authVersion`.
- Invalidates other outstanding password-reset tokens for that user.
- Clears the current request's refresh cookie.
- Sends a password-change notification email.
- Does not automatically log the user in.

#### Errors

| Status | Message                                            |
| ------ | -------------------------------------------------- |
| `400`  | Validation failed                                  |
| `400`  | `Invalid or expired password reset token`          |
| `429`  | `Too many reset attempts. Please try again later.` |
| `500`  | Unexpected failure                                 |

Reset attempts are limited to 10 requests per source IP per 60-second window.

#### Frontend Notes

After a successful reset:

1. Clear the current frontend authentication state.
2. Display the success message.
3. Redirect to login.
4. Require fresh authentication.

Password resets invalidate previously issued access tokens through
authorization-version changes. Existing refresh tokens also fail their
user-version check.

### 3.10 Change Password

`PATCH /api/v1/auth/change-password`

**Purpose:** Change the authenticated user's existing password.

**Authentication:** Required.

#### Headers

```http

```

#### Request Body

```json

  "currentPassword": "OldPassword123!",

```

#### Validation

| Field             | Type   | Required | Rules                                        |
| ----------------- | ------ | -------- | -------------------------------------------- |
| `currentPassword` | string | Yes      | Non-empty                                    |
| `newPassword`     | string | Yes      | Minimum 8 characters, maximum 72 UTF-8 bytes |

The new password must differ from the current password.

The schema is strict: unknown fields are rejected.

#### Success — `200 OK`

```json
{
  "message": "Password changed successfully. Please log in again."
}
```

#### Errors

| Status | Message                                                |
| ------ | ------------------------------------------------------ |
| `400`  | Validation failed                                      |
| `400`  | `This account does not have a password`                |
| `400`  | `Current password is incorrect`                        |
| `400`  | `New password must differ from current password`       |
| `401`  | Authentication required / invalid token                |
| `404`  | `User not found`                                       |
| `409`  | `Password was changed concurrently. Please try again.` |
| `500`  | Unexpected failure                                     |

#### Frontend Notes

- Google-only accounts cannot use this endpoint unless they have a local
  password.
- A successful password change invalidates existing access and refresh
  credentials.
- Clear frontend authentication state and redirect to login.
- Password changes are protected against concurrent updates using a database
  compare-and-swap operation.

## 4. Role-Based Access Control (RBAC)

The system uses database-driven RBAC rather than hardcoded role checks.

### Architecture

A user belongs to exactly one role.

A role can have multiple permissions, and the same permission can be assigned to
multiple roles.

The frontend must check permission keys to determine whether a feature should be
displayed or enabled.

### Default Seeded Roles

| Role       | Initial Permissions                                                                                                    |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| `ADMIN`    | `user:read`, `user:create`, `user:update`, `role:read`, `role:create`, `role:update`, `role:delete`, `permission:read` |
| `EMPLOYEE` | `user:read`                                                                                                            |
| `USER`     | None                                                                                                                   |

These are seeded defaults and can change through RBAC management operations.

### Seeded Permission Definitions

| Permission        | Description      |
| ----------------- | ---------------- |
| `user:read`       | Read users       |
| `user:create`     | Create users     |
| `user:update`     | Update users     |
| `role:read`       | Read roles       |
| `role:create`     | Create roles     |
| `role:update`     | Update roles     |
| `role:delete`     | Delete roles     |
| `permission:read` | Read permissions |

**Important:** `user:create` is seeded but no RBAC user-creation endpoint is
currently implemented. Registration is public and assigns the default role.

### Endpoint Summary

| Method   | Endpoint                   | Required Permission | Success |
| -------- | -------------------------- | ------------------- | ------- |
| `GET`    | `/rbac/permissions`        | `permission:read`   | `200`   |
| `GET`    | `/rbac/roles`              | `role:read`         | `200`   |
| `POST`   | `/rbac/roles`              | `role:create`       | `201`   |
| `PATCH`  | `/rbac/roles/:roleId`      | `role:update`       | `200`   |
| `DELETE` | `/rbac/roles/:roleId`      | `role:delete`       | `204`   |
| `PATCH`  | `/rbac/users/:userId/role` | `user:update`       | `200`   |
| `GET`    | `/rbac/users`              | `user:read`         | `200`   |

All paths are relative to `/api/v1`.

**All RBAC endpoints require a valid Bearer access token.**

### 4.3 Create Role

`POST /api/v1/rbac/roles`

**Required permission:** `role:create`

#### Request Body

```json

  "name": "Manager",

```

#### Validation

| Field         | Type     | Required | Rules                                                 |
| ------------- | -------- | -------- | ----------------------------------------------------- |
| `name`        | string   | Yes      | Trimmed, minimum 2 characters, converted to uppercase |
| `permissions` | string[] | No       | Existing permission keys, no duplicates               |

If omitted, `permissions` defaults to `[]`.

An empty array is valid.

Permission strings are individually trimmed before duplicate detection and
lookup.

#### Success — `201 Created`

```json
{
  "data": {
    "id": "role-uuid",
    "name": "MANAGER",
    "permissions": [
      {
        "permission": {
          "key": "user:read",
          "description": "Read users"
        }
      },
      {
        "permission": {
          "key": "role:read",
          "description": "Read roles"
        }
      }
    ]
  }
}
```

**Response-shape distinction:** The create endpoint returns permission records
wrapped in a nested `permission` object.

This differs from `GET /roles`.

#### Errors

| Status | Message                                |
| ------ | -------------------------------------- |
| `400`  | Validation failed                      |
| `400`  | `One or more permissions do not exist` |
| `401`  | Authentication error                   |
| `403`  | `Forbidden`                            |
| `409`  | `Role already exists`                  |
| `500`  | Unexpected failure                     |

#### Frontend Notes

- Convert role names to uppercase for display consistency, although the backend
  also handles this.
- Retrieve available permissions before rendering the form.
- Refresh the role list after successful creation.
- A new role has no users until explicitly assigned.

**Required permission:** `role:update`

#### Path Parameters

| Parameter | Type   | Required |
| --------- | ------ | -------- |
| `roleId`  | string | Yes      |

`roleId` represents a UUID.

**Implementation detail:** A UUID schema exists in the source but is not

| Status | Message                                |
| ------ | -------------------------------------- |
| `400`  | Validation failed                      |
| `400`  | `One or more permissions do not exist` |
| `401`  | Authentication error                   |
| `403`  | `Forbidden`                            |
| `404`  | `Role not found`                       |
| `409`  | `Role already exists`                  |
| `500`  | Unexpected failure                     |

#### Critical Behavior

When `permissions` is supplied, it **replaces the complete permission set**,
rather than merging with existing permissions.

Every successful role update increments `authVersion`, even when only the name
changes.

Existing access tokens referencing the previous role version become invalid.

Valid refresh sessions may obtain updated access tokens with the role's latest
permissions.

#### Frontend Notes

After updating a role:

- Refresh role data.
- Update permission-dependent UI.
- Consider refreshing the current session if the modified role belongs to the
  signed-in user.
- Handle revoked access tokens through the standard token-refresh flow.

### 4.5 Delete Role

`DELETE /api/v1/rbac/roles/:roleId`

**Required permission:** `role:delete`

#### Path Parameters

| Parameter | Type   | Required |
| --------- | ------ | -------- |
| `roleId`  | string | Yes      |

#### Success — `204 No Content`

No JSON body.

#### Behavior

When deleting a role:

1. The backend verifies that the role exists.
2. Prevents deletion of the configured default role.
3. Reassigns users belonging to the deleted role to the default role.
4. Deletes the target role.
5. Removes its role-permission relationships through cascading deletion.
6. Removes the deleted role's authorization-version cache entry.

User reassignment and role deletion occur within one PostgreSQL transaction.

#### Errors

| Status | Message                                                |
| ------ | ------------------------------------------------------ |
| `401`  | Authentication error                                   |
| `403`  | `Forbidden`                                            |
| `404`  | `Role not found`                                       |
| `409`  | `The default role cannot be deleted`                   |
| `500`  | Default-role configuration failure or unexpected error |

#### Frontend Notes

- Show a confirmation dialog before deletion.
- Warn that affected users will be reassigned to the default role.
- Do not allow deleting the default role in the UI when it can be identified.
- Refresh the roles and users lists after deletion.
- Do not parse JSON from the `204` response.

**Security implementation note:** User reassignment during role deletion does
not increment each affected user's `authVersion`. The deleted role is no longer
present in PostgreSQL, so tokens referencing it will fail authentication once
their role-version lookup is performed. A refresh token can still be used to
obtain a token with the user's newly assigned default role, subject to the
normal refresh checks.

## 7. Token Revocation and Authorization Updates

The system uses authorization versions to reject outdated JWTs.

### Role Version

Each role has an `authVersion`.

When a role is updated:

- Its version increments.
- Redis stores the latest version.
- Access tokens with the previous role version are rejected.

### User Version

Each user has an `authVersion`.

The version increments when:

- A user's role is changed.
- A password reset succeeds.
- An authenticated password change succeeds.

Previously issued access tokens are then rejected.

A password change or reset also prevents old refresh tokens from being used
successfully because refresh validation checks the user's current version.

### Frontend Handling

A `401` response can mean:

- Access token expired.
- Token signature is invalid.
- Role permissions changed.
- User role changed.
- Password changed.
- User or role was removed.

The frontend should attempt a controlled refresh when appropriate.

If refresh fails, remove authenticated state and require login.

A `403` response means the request was authenticated but the token does not
contain the required permission. Do not treat ordinary `403` responses as
token-expiration events.

## 10. Current Implementation Limitations

The following functionality is **not implemented as an API endpoint** in the
reviewed source:

| Capability                                    | Status          |
| --------------------------------------------- | --------------- |
| Create permission definitions                 | Not implemented |
| Update permission definitions                 | Not implemented |
| Delete permission definitions                 | Not implemented |
| Create users through RBAC administration      | Not implemented |
| Update general user profile                   | Not implemented |
| Delete users                                  | Not implemented |
| List individual user details by ID            | Not implemented |
| Change account email                          | Not implemented |
| Link an existing password account to Google   | Not implemented |
| Unlink OAuth providers                        | Not implemented |
| Paginate users or roles                       | Not implemented |
| Server-side search/filter users               | Not implemented |
| Per-user permission overrides                 | Not implemented |
| Resource-level ownership / ABAC               | Not implemented |
| Frontend redirect after Google OAuth callback | Not implemented |
| Global CORS configuration                     | Not implemented |
| Automated API integration tests               | Not implemented |

### Backend Contract Issues Worth Addressing

**1. Google OAuth frontend handoff**

The Google callback currently sends the access token in a backend JSON response.
A dedicated frontend handoff strategy is needed for a seamless SPA login
experience.

**2. Inconsistent role response structures**

Create, update, and list operations return different role shapes. Standardizing
them would reduce frontend transformation logic.

**3. Path parameter validation**

A `roleParamsSchema` exists but is not connected to the update/delete routes.
User ID path parameters likewise have no explicit route-level Zod validation.

**4. Cross-origin browser support**

The Express application does not currently install CORS middleware. Cookie-based
authentication requires coordinated frontend/backend origin and cookie
configuration.

**5. Missing pagination**

User and role listing endpoints return complete result sets, which may become
inefficient as the dataset grows.

**6. Password input consistency**

Registration has a minimum eight-character password rule but no explicit
maximum. Password reset enforces at most 72 characters, while authenticated
password changes enforce 72 UTF-8 bytes.

These rules should eventually be standardized.

**7. Cookie and session behavior**

Logout clears the browser's refresh cookie and removes the supplied refresh
session, but it does not immediately revoke an otherwise-valid access JWT.

**8. Authentication and configuration errors**

Some missing application configuration cases use generic `Error` instances,
producing the standard `500 Internal server error` response. Other known
configuration failures use `AppError` with a more specific message.
